**Blockchain / Chain** (`Blockchain` and its nested `Chain`)
51. Stuck BToken reorg after a failed undo (found 2026-10-12): since `ActionExtensionMethods.Announce` catches every listener exception (plan "Divers Blockchain bug fixes", step 2), a non-protocol exception while BToken undoes a block (`RollBack` → `TryLoadBlock`, `block.Parse`, `Token.RollBack`) only stops BToken's reaction: the applied tip stays on that block, the blocks undone before it are re-queued, chains already switched stay switched, and in `RemoveHeaderPlaceholder` the placeholder stays although its Bitcoin block is gone. Bitcoin never re-announces that rollback, so the removal is retried only when a lower root-chain placeholder is removed later (its rollback first undoes the stale block); until then BToken keeps a block applied whose anchor Bitcoin no longer carries, and the miner would build on that orphan block, so other nodes reject those blocks and the slots it wins are wasted. The next `UpdateTipBlockchain` re-applies the queued blocks and retries the reorg. A transient error recovers this way; a deterministic one (e.g. a stored block that fails `block.Parse`) fails on every retry, so BToken stays on the old branch for good, visible only as console lines. Re-verified 2026-10-20: the pool is no longer involved, since it reacts only to `OnBlockRolledBack` after `Token.RollBack` succeeded, and the former deterministic cause (pool casting every output to P2PKH) is gone. Decision with the user 2026-10-20: no code fix beyond the console log; the operator process decides to restart the node. Re-verified 2026-10-28: the startup double apply is gone (accounts and blocks share one LiteDB transaction), and at startup `BlockchainBToken.RollBackUnanchored` removes the stored BToken block whose anchor Bitcoin no longer carries, so a restart recovers a transient error; a deterministic undo error throws again there, out of `Node.Start`. Re-verified 2026-10-29: a failed undo now rolls back its LiteDB transaction before the exception leaves `Blockchain.RollBack`.

**BToken accounts** (`TokenBToken`)
55. `TXOutputBitcoin` possibly redundant (found 2026-10-29): its only remaining purpose is `PublicKeyHash160`, read by `TokenBitcoin.TryAddTXOutputWallet` to recognize the wallet's own P2PKH outputs; its `Data` field is unused. The parser could store the hash in `TXOutput.IDAccount`, which BToken uses for the account ID, and the class could go. Re-verified 2026-10-29: BToken's `TXOutputP2PKH` already parses a P2PKH script into `IDAccount`; `TXOutputBitcoin` is also used for unrecognized outputs (`TXOutput` is abstract) and for the anchor's change output.
54. Pool half-updated on a failed removal (found 2026-10-20): `PoolTXBToken.RemoveTXs`, the `OnBlockInserted` listener, removes a confirmed TX from `TXsByHash` before checking that it is its sender's first waiting TX in `TXsByIDAccountSource`. When the check throws, `AnnounceBlock` logs it, the TX stays in `TXsByIDAccountSource` and `OutputValuesByIDAccount` without its `TXsByHash` entry, and the block's later TXs stay in the pool. The block and the accounts are unaffected.

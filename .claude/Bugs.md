**Blockchain / Chain** (`Blockchain` and its nested `Chain`)
47. BToken root on a pruned Bitcoin stub: BToken lives only on the stretch of Bitcoin blocks that is stored (all headers, only the newest ~200 blocks). Once older Bitcoin blocks are pruned, the oldest placeholder of that stretch has an unknown predecessor → `InsertHeaderPlaceholder` ignores it, and every later placeholder too → BToken tree never grows. The tree needs a root inside the stored stretch. Dormant until pruning exists; to be solved in a separate pruning plan (moved out of plan "Divers Blockchain bug fixes" 2026-10-11). Design agreed with the user 2026-10-11: Bitcoin always prunes: it keeps the header chain from its checkpoint genesis (height 900000) forever, but only the last N blocks (N ≈ 200) for reorgs. BToken keeps its own header chain forever, each header with its Bitcoin parent, and rebuilds its tree from it at startup, because anchors live only in Bitcoin blocks, not in Bitcoin headers. BToken also keeps only the last N blocks. Its accounts are stored as a main database at tip minus N plus a diff database built from the N stored blocks, which together give the state at the tip: rolling back a block drops its diff, pruning a block merges its diff into the main database. Today `TokenBToken` writes every block straight into the main account DB, so this needs a restructured token storage. A fresh BToken node downloads a peer's main database at tip minus N, checks it against `HashDatabase` in the BToken header of that block, then downloads the last N blocks and applies them up to the tip.
51. Stuck BToken reorg after a failed undo (found 2026-10-12): since `Blockchain.AnnounceBlock` catches every listener exception (plan "Divers Blockchain bug fixes", step 2), a non-protocol exception while BToken undoes a block (`RollBack` → `TryLoadBlock`, `block.Parse`, `Token.RollBack`) only stops BToken's reaction: the applied tip stays on that block, the blocks undone before it are re-queued, chains already switched stay switched, and in `RemoveHeaderPlaceholder` the placeholder stays although its Bitcoin block is gone. Bitcoin never re-announces that rollback, so the removal is retried only when a lower root-chain placeholder is removed later (its rollback first undoes the stale block); until then BToken keeps a block applied whose anchor Bitcoin no longer carries, and the miner would build on that orphan block, so other nodes reject those blocks and the slots it wins are wasted. The next `UpdateTipBlockchain` re-applies the queued blocks and retries the reorg. A transient error recovers this way; a deterministic one (e.g. a stored block that fails `block.Parse`) fails on every retry, so BToken stays on the old branch for good, visible only as console lines. Re-verified 2026-10-20: the pool is no longer involved, since it reacts only to `OnBlockRolledBack` after `Token.RollBack` succeeded, and the former deterministic cause (pool casting every output to P2PKH) is gone. Decision with the user 2026-10-20: no code fix beyond the console log; the operator process decides to restart the node. Re-verified 2026-10-28: the startup double apply is gone (accounts and blocks share one LiteDB transaction), and at startup `BlockchainBToken.RollBackUnanchored` removes the stored BToken block whose anchor Bitcoin no longer carries, so a restart recovers a transient error; a deterministic undo error throws again there, out of `Node.Start`.

**BToken accounts** (`TokenBToken`)
53. BToken TX output format inconsistent (found 2026-10-12): `TXBToken.ParseTXOutputBToken` reads value (into an unused local) + script length, then `TXOutputP2PKH(buffer, ref index)` reads a type byte at the script start (0x76, not `TypesToken.P2PKH`), so `Value` stays 0, `IDAccount` stays null and the index advances by one byte only → the rest of the TX misparses. `TXBToken.Serialize` writes a third format (type byte + script, no value), and an unrecognized output is added as null. Its loop also casts every output to `TXOutputP2PKH`, so an anchor output throws InvalidCastException (re-verified 2026-10-29 after plan "Anchor Serialization", which fixed this cast only in `TXBitcoin.Serialize`). → every BToken block with a coinbase reward fails `VerifyCoinbase` or misparses; no real block can be applied or undone today. Fix: one output format for serialize and parse.
55. `TXOutputBitcoin` possibly redundant (found 2026-10-29): its only remaining purpose is `PublicKeyHash160`, read by `TokenBitcoin.TryAddTXOutputWallet` to recognize the wallet's own P2PKH outputs; its `Data` field is unused. The parser could store the hash in `TXOutput.IDAccount`, which BToken uses for the account ID, and the class could go.
54. Pool half-updated on a failed removal (found 2026-10-20): `PoolTXBToken.RemoveTXs`, the `OnBlockInserted` listener, removes a confirmed TX from `TXsByHash` before checking that it is its sender's first waiting TX in `TXsByIDAccountSource`. When the check throws, `AnnounceBlock` logs it, the TX stays in `TXsByIDAccountSource` and `OutputValuesByIDAccount` without its `TXsByHash` entry, and the block's later TXs stay in the pool. The block and the accounts are unaffected.

**Mining** (`InsertBlockMined` currently commented out in `Miner`)
23. No re-mine when the BToken tip changes: `Miner.OnBlockBitcoinInserted` mines right after the Bitcoin block is applied, before the newest placeholder's block has been announced and downloaded → it mines on the previous BToken tip. Re-mine once the newest block is inserted.
24. Stale anchor TXs: only one open anchor at a time; each re-mine must replace the previous unconfirmed anchor (RBF, same inputs, higher fee), else a stale anchor can win a later slot and waste it.
27. `TokenBToken.CreateTXCoinbase` never adds `tXOutput` to `tX.TXOutputs` (and sets no `Value`) → block reward lost.
28. `TokenBitcoin.TryCreateTXAnchor` doesn't mark spent inputs → next anchor double-spends. Also `OutputsSpendableConfirmed` is never filled (`InsertBlock` fills `OutputsSpendable`) → always returns false.
29. Starting the miner: `IsMining` is never set true; when switched on (future RPC), mine immediately instead of waiting for the next Bitcoin block.

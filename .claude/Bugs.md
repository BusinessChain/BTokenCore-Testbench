**Blockchain / Chain** (`Blockchain` and its nested `Chain`)
51. Stuck BToken reorg after a failed undo (found 2026-10-12): since `ActionExtensionMethods.Announce` catches every listener exception (plan "Divers Blockchain bug fixes", step 2), a non-protocol exception while BToken undoes a block (`RollBack` → `TryLoadBlock`, `TryParseBlockStored`, `RollBackBlock`) only stops BToken's reaction: the applied tip stays on that block, the blocks undone before it are re-queued, chains already switched stay switched, and in `RemoveHeaderPlaceholder` the placeholder stays although its Bitcoin block is gone. Bitcoin never re-announces that rollback, so the removal is retried only when a lower root-chain placeholder is removed later (its rollback first undoes the stale block); until then BToken keeps a block applied whose anchor Bitcoin no longer carries, and the miner would build on that orphan block, so other nodes reject those blocks and the slots it wins are wasted. The next `UpdateTipBlockchain` re-applies the queued blocks and retries the reorg. A transient error recovers this way; a deterministic one (e.g. a stored block that fails `block.Parse`) fails on every retry, so BToken stays on the old branch for good, visible only as console lines. Re-verified 2026-10-20: the pool is no longer involved, since it reacts only to `OnBlockRolledBack` after `Token.RollBack` succeeded, and the former deterministic cause (pool casting every output to P2PKH) is gone. Decision with the user 2026-10-20: no code fix beyond the console log; the operator process decides to restart the node. Re-verified 2026-10-28: the startup double apply is gone (accounts and blocks share one LiteDB transaction), and at startup `BlockchainBToken.RollBackUnanchored` removes the stored BToken block whose anchor Bitcoin no longer carries, so a restart recovers a transient error; a deterministic undo error throws again there, out of `Node.Start`. Re-verified 2026-10-29: a failed undo now rolls back its LiteDB transaction before the exception leaves `Blockchain.RollBack`. Re-verified 2026-10-30: a stored block that is missing or fails to parse now makes `RollBack` throw an `InvalidOperationException` naming the height, instead of a `NullReferenceException` or the parser's `ProtocolException`; the behaviour above is unchanged.

**BToken TX pool** (`BlockchainBToken.PoolTXBToken`)
54. Pool keeps TXs that an inserted block made invalid, and mining halts (found 2026-10-20, widened 2026-10-30 now that relayed TXs reach the pool): `PoolTXBToken.RemoveTXs`, the `OnBlockInserted` listener, removes only block TXs whose hash is in the pool and never re-checks the remaining pool TXs against the new account state (`DropTXsNoLongerCoveredByBalance` runs only in `ReturnTXs` after a rollback). Scenario: sender A sends TX a5 (nonce 5) to our node and a different TX a5' with the same nonce, e.g. a fee bump, to another miner, whose block confirms a5'. a5 stays in our pool; `BlockchainBToken.MineBlock` takes it through `GetTXs`, `InsertTXs` throws a `ProtocolException` on the nonce in `Account.SpendTX`, and `OnTipChanged.Announce` only logs it, so our miner skips every tip change until a rollback or a restart clears the pool. A's later TXs are also refused by `AddTX`, since it expects nonce 7. A spend from A's account that never passed our pool, or a block with a5' and our a6, has the same effect; the latter also hits the original defect: `RemoveTXs` removes a6 from `TXsByHash`, then throws because a6 is not A's first waiting TX, leaving a6 in `TXsByIDAccountSource` and `OutputValuesByIDAccount` and the block's later TXs in the pool. Since plan "TX Throttling", the dispatcher also announces such dead TXs from the pool ranking, which spends relay budget per peer on TXs every peer refuses. Fix idea: on block insert, remove every confirmed TX regardless of order, then re-validate the pool as `ReturnTXs` does.

**Messages**
15. Honest TX relay breaks the receiver's own DoS rule (reframed 2026-10-30, now reachable with the live TX relay): `TXMessage.IncrementDOSMonitor` charges every received TX byte against 2 MB with a drain of 1 MB per 10 minutes, but the receiver itself requested those TXs: `InvMessage.Run` sends getdata for every announced hash not in the pool, without a budget and without recording what it requested. A peer that relays more than about 1 MB of TXs per 10 minutes, which is the BToken block capacity, is dropped for delivering what we asked for. Fix in progress in plan "TX Throttling": every node throttles its own announcements per peer to the receive policy, highest fee per byte first. This bounds the receiver too, because `InvMessage.Run` requests only hashes the peer announced, so an honest sender never makes an honest receiver exceed its level.
55. Free repeated chain download (found 2026-10-30): `GetDataMessage.Run` refunds the getdata count (`DOSMonitor.Decrement(1)`) for a served block higher than `HeightBlockDownloadedLast`, but overwrites `HeightBlockDownloadedLast` with every served block's height, also a lower one. A peer pays 1 to request block 1 and then re-downloads the whole chain for free, as often as it likes. Re-verified 2026-10-30. Fix idea: keep the maximum height instead of overwriting.

**Network**
17. `COUNT_MAX_OUTBOUND_CONNECTIONS = 1` and hard-coded IP in `Network.GetPeer` (used by both the Bitcoin and the BToken network). The BToken network has no `SeedAddresses`, so it has no peer discovery at all. `AddressMessage` is never registered in `Network.CreateStateMachineProtocol`, so a received "addr" lands in `UnknownMessage` (10 KB buffer, larger payloads drop the peer); its `Run` is empty and its parsing sits in a constructor the receive path never calls. Low priority (user, 2026-10-29).
